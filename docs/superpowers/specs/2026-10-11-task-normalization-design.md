# 待办规范化设计

用户已确认：新增结构化字段并兼容旧待办，不重新解析全部历史邮件。

## 数据与显示规则

保留 PlannerItem.text、created_date 和所有既有字段；新增可选 schedule。旧 JSON 无需迁移即可读取。schedule 保存类型、公司及原名称、岗位、轮次、开始/结束日期时间、时间语义、时区、地点、链接、备注、邮件 UID/主题/时间和时间依据、待确认标记。

类型固定为面试、笔试、测评、宣讲会、投递、签约、其他。仅明确的名称别名归一化；不同主体不合并。没有信息则留空，不猜测岗位、轮次或日期。时间分为开始、截止、时间段、未知；相对日期以邮件发送日期为基准。日期和时间严格校验。无日期事项留在待办列表并标记待确认，不伪装成已确定的日历事件。

规则和 AI 经过同一个规范化入口。统一标题为“[类型] 公司 · 岗位 · 轮次”，缺少公司时使用“公司待确认”；其他事项可使用提取出的行动标题。详情分别展示时间、地点、链接和备注，列表与日历共用展示组件。手工修改 text 后保留该文字，不重新覆盖；旧待办和手动待办继续显示原文。

去重只比较结构化事件：公司、类型、岗位、轮次、时间语义及起止日期时间。信息不足时仅在同一邮件中比较完整规范化内容；同邮件的不同事项应保留。后续提醒仅在事件身份明确一致时去重，不覆盖人工编辑。现有历史邮件 UID 不重扫。

## 实施范围

新增独立 task 模块承载规范化、时间解析和事件比较。规则可返回多个明确的事件行；AI 输出可包含多个事件。前端复用 TaskContent 展示结构化内容。兼容编辑和日历数据同步。保持现有排序和跨日行为。

## 验收

- 同一邮件的规则/AI输入归一化后一致。
- 不猜测缺失日期；非法日期时间留空并待确认。
- 邮件“明天”和年末日期不取扫描当天作为基准。
- 开始、截止、时间段分别显示。
- 多事项不被同邮件 UID 一概拦截；不同时间/岗位/轮次不误去重。
- 旧 JSON、手动文字、人工编辑与完成状态保持兼容。
- Rust 回归测试、前端类型检查与构建通过，发布包能够构建。
